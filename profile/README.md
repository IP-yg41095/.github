<h2>可以，但限制不在地址数量上</h2>
<p>一台服务器绑几十个地址在技术上没有障碍，操作系统和网卡都支持。真正限制你的是四处：网卡的承载能力、上游线路的带宽、系统对策略路由的支持程度、以及你管理这些地址的能力。</p>
<p>所以问「能配几个」的正确方式是先问「打算怎么用」。用途不同，能支撑的数量差别很大。</p>

<h2>四处理论与实际的限制</h2>
<p>网卡：一个地址绑定不占多少资源，几十个没问题，但每个地址都会产生额外的入向流量处理。带宽：所有地址共享同一条线路，地址越多每条分到的越少。策略路由：规则数量随地址增长，规则过多会影响转发效率。</p>
<p>管理能力：这是最容易被忽略的一项。地址一多，谁用哪个、什么时候换过、有没有交叉，全靠记录。没有记录，二十个地址就能管成一团乱麻。</p>

<h2>网卡与地址绑定</h2>
<p>常见的做法是在网卡上添加多个地址，或者用虚拟网卡给每个地址单独建一个。前者简单，后者清晰。如果用虚拟网卡，每个地址的流量可以单独控制，排障也容易。</p>
<p>绑定之后要确认路由。多地址场景里最常见的问题是「地址绑上了但出不去」，原因是回程路由没有对应配置。绑完立刻测一次出网，别攒着一起测。</p>

<h2>策略路由：决定谁走哪个地址</h2>
<p>策略路由的核心是「规则表 + 优先级」。建立独立的规则表，把「某个来源走某个地址」的对应关系写进去，再设置优先级，让特例在通用规则之前匹配。</p>
<p>规则顺序写错是最常见的问题。表现是「配了但没生效」，查半天发现是通用规则先被匹配了。写规则时按「越具体越靠前」排列，基本不会错。</p>

<h2>让程序用对地址</h2>
<p>地址绑好、路由配好，还有一步：程序要真的从指定地址出网。多数程序默认用系统主地址，不管绑了几个，出网的都是同一个。</p>
<p>解决办法有两种：程序支持指定源地址时直接指定；不支持时用策略路由按用户或按来源分流。前者简单，后者通用。先看程序能力，再决定方案。</p>

<h2>验证方法</h2>
<p>逐地址验证，不是只测一个。从每个地址分别发起一次外部访问，看对方看到的源地址。全部对得上，才算配置完成。</p>
<p>验证时最好用不同的目标站点。某些站点会缓存连接信息，同一目标多次测试可能得到旧结果，导致误判。</p>

<h2>五个常见错误</h2>
<p>一是地址绑了没配路由，出不去。二是策略规则顺序错，特例被覆盖。三是程序不认源地址，实际出网仍是主地址。四是多个地址共用同一个出站队列，互相抢占。五是记录缺失，没人知道哪个地址归谁。</p>
<p>五个错误里前三个是技术问题，后两个是管理问题。后者更难修，也更常见。</p>

<h2>常见问答</h2>
<h3>一台服务器能配多少个住宅地址？</h3>
<p><strong>答：</strong>技术上很多，实际取决于带宽与管理能力。建议按「每条地址有明确归属」来控制数量。</p>
<h3>需要多网卡吗？</h3>
<p><strong>答：</strong>不是必须，但多地址场景下多网卡会让配置与排障都更清晰。</p>
<h3>地址之间会互相影响吗？</h3>
<p><strong>答：</strong>会共享带宽与 CPU。地址越多，每条分到的资源越少。</p>
<h3>怎么知道配置生效了？</h3>
<p><strong>答：</strong>只能实测出口地址。配置文件写得对不代表行为对。</p>
